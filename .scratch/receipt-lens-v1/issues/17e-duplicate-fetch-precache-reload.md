# 17e: Stop the cold visit fetching the shell twice (worker precache uses `cache: "reload"`)

**What to build:** the install-time precache in `packages/pwa/src/sw.ts` fetches every shell entry with
`cache: "reload"`, so on a cold visit the document downloads `/assets/index-*.js` and the worker downloads it
again. This ticket decides whether that freshness is required and, if it is not, makes it conditional — without
weakening what `DECISIONS/0027` W1.1's completeness guard and W13.1's install-failure rule guarantee.

**Blocked by:** 17c (ETag on code assets) — the header work lands first and this ticket's fix is measured against
the post-17c numbers, not the pre-17c ones.
**Blocks:** nothing. **18 does not wait on this.**
**Status:** ready-for-agent, **post-v1** — parked deliberately, see "Why it is post-v1".
**Effort:** ~3 h · **Roadmap:** workstream 3A · **Milestone:** post-M3

## Why it exists

Ticket 17b measured the cold visit at **21,719,232 B over 22 requests for 17 assets**. The asset set is
21,466,286 B; the remaining **252,946 B is bytes the same visit paid twice**, because the worker re-fetches what
the document just fetched:

| Asset | Cold fetches | Duplicated bytes |
|---|---:|---:|
| `/assets/index-*.js` (entry, shell + core + OCR glue) | 2 | 242,513 |
| `/assets/index-*.css` | 2 | 7,980 |
| `/assets/cache-names-*.js` (worker module) | 3 | 1,910 |
| `/assets/rolldown-runtime-*.js` | 2 | 543 |
| **Total** | | **252,946** |

That is 1.1% of the first download, and 96% of it is the entry chunk alone. It is generated by
`fetch(entry.url, { cache: "reload" })` in the install handler, and `DECISIONS/0027` W6 pins `cache: "reload"` as
how a *version probe* bypasses the cache it is checking — which is the right reason for the model-manifest probe
and a debatable reason for precaching the app's own static chunks.

## Why it is post-v1 and not folded into 17c

It is **not a correctness fix.** A cold visit that fetches the shell twice is a slightly slower first download,
not a wrong one, and every published claim about it is currently honest: the table names the count of repeat
fetches and the generator derives the delta from the two committed artifacts so the sentence cannot rot.

Folding it into 17c would also break the rule 17b's T7 and `DECISIONS/0012` F3 are built on — one variable per
ticket. 17c changes a response header and regenerates two artifacts; this changes *what the worker does at
install*, which is a different mechanism with a different failure mode (an install that trusts a cached copy of
its own shell has to answer W1.1's completeness guard and W13.1's "install fails loudly" rule all over again).
Two changes that each move `footprint.json` must not land in one commit, or the pre/post delta becomes
unattributable — the exact error W14.1's dated archive exists to prevent.

## What it must decide before it can be built

1. **Is the reload load-bearing?** The candidate argument for keeping it: precache freshness is what makes the
   shell cache name (`v<digest>`, W3) meaningful — a digest computed from the manifest, holding bytes that were
   fetched unconditionally fresh. If a precache may be served from the HTTP cache, does `v<digest>` still mean
   what it says? The candidate argument for dropping it: every shell asset is content-hashed by the build, so a
   cached copy *cannot* be a stale one under a different name, which is the §9 content-hashing rule doing the
   job `reload` is doing now.
2. **What breaks if the precache hits a poisoned entry.** W13.1 pins that a failed precache fails the install
   loudly. A cached 200 is not a failure; a cached *wrong* byte is. The answer has to be a test, not a sentence.
3. **The measurement.** Cold bytes are expected to fall by ~253 KB to 21,466,286 B, and warm is unaffected. Both
   artifacts regenerate in this ticket's commit exactly as 17c's do, with the ±0 cross-check intact.

## Scope may grow, depending on what 17c measures

Ticket 17c adds a content `ETag` + `no-cache` to code assets. If 17c's warm number does **not** fall — i.e. the
browser never sends `If-None-Match` for the worker's module import — the explanation is this ticket's mechanism:
`fetch(entry.url, { cache: "reload" })` bypasses the HTTP cache, so precaching never populates a copy that could
be revalidated. **In that case 17e owns both symptoms of one mechanism**: the cold visit fetching the shell
twice, and the warm visit being unimprovable by an origin-side validator. 17c records the finding and points
here; it does not try to fix it, because the fix is a change to what the worker does at install.

If 17c's number *does* fall, this ticket keeps its original, narrower scope: the cold repetition only.
